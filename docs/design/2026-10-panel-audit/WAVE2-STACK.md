# Волна 2: стек панели

Записано 2026-10-08 по просьбе владельца. Это решения и предложения для планирования волны 2, а не план.
Волна 1.5 доводится на текущем стеке.

## Откуда текущий стек

Панель появилась 2026-08-11 как `h3 web` в MLX-форке на Маке: локальная страница для одного человека.
Сервер написан на stdlib Python (`http.server`), чтобы не добавлять зависимостей в окружение MLX.
Клиент — ванильный JS без сборки. Тогда это было оправдано.

К октябрю 2026 панель выросла: `web.py` — 6762 строки, `app.js` — 5463 строки. Ручной стек обходится дорого,
и находки ревью волн 1 и 1.5 это показывают:

- **Сервер.** Роутинг, разбор тела, проверка полей и контракт ошибок написаны руками. Отсюда находки
  вида «400 вместо 404», «сдвинулся порядок проверок», «исключение отдало 500».
- **Клиент.** Состояние синхронизируется вручную (`draftEpoch`, `syncDraftFromDom`): «перерисовка затёрла
  правки», ручная синхронизация полей и черновика. Тесты UI идут на самописном фейковом DOM в Node,
  и моки расходятся с реальными обработчиками.

## Решения

### 1. Сервер: FastAPI + Pydantic, переносить постепенно
- Контракт API уже есть, и около 1900 HTTP-тестов его закрепляют. Маршруты переносятся группами,
  каждую группу проверяют те же тесты.
- `project.py`, `assemble.py`, `queue.py`, `worker.py`, `engines/`, `library.py` от веб-слоя не зависят
  и переносятся как есть.
- Что даёт FastAPI: модели запросов и ответов с проверкой, единый обработчик ошибок, OpenAPI.
  OpenAPI — готовая основа для MCP-сервера, через который Hermes будет управлять панелью; это давнее
  желание владельца.
- Вместо опроса `/api/state` каждые N секунд — SSE: прогресс сцен, очередь, плашка GPU, уведомления.

### 2. Клиент: React + Vite + TypeScript
- Редизайн волны 2 (макет A, `mockups/variant-a`) всё равно переписывает интерфейс. Писать его на React
  дешевле, чем дописывать редизайн в 5,5 тыс. строк ручного JS.
- Типы клиента генерируются из OpenAPI (`openapi-typescript`), чтобы клиент и сервер не расходились.
- Сборка внутри Docker-образа (multi-stage), на сервере ничего не добавляется.
- Порядок: сначала сервер на FastAPI, потом новый клиент поверх готового API.

### 3. Хранилище: SQLite, без Postgres
Сейчас состояние лежит в файлах: `project.json` под flock, карточки библиотеки в каталогах,
история в jsonl. Это даёт:
- гонки, которые закрывали руками: удаление карточки, воскрешение каталога, `.trash`;
- «кто использует карточку» — чтение всех `project.json` под замком;
- выборки (проекты по статусу, история по сцене) — обход файлов.

Предложение:
- **SQLite** в одном файле в outdir с WAL и транзакциями. Таблицы: проекты, сцены, карточки
  и их версии, связи «проект/сцена → карточка», история оценок времени.
  - Внешнего сервиса нет, бэкап — копия файла.
  - Ссылочная целостность: удалить используемую карточку не даст внешний ключ, а не ручной скан.
- **Медиа остаются на диске** (клипы, кадры, картинки карточек), в БД хранятся только пути.
- **Postgres не нужен.** Пользователь один, данных мало, сервис ради этого держать незачем.
- **Миграция.** Импорт существующих `project.json` и каталогов библиотеки одним скриптом. Месяц
  держать запасное чтение из файлов.

### 4. Очередь: без Redis
- GPU один, воркер один, задача идёт минуты и часы, задач — единицы в час. Сильная сторона Redis —
  скорость и множество потребителей — здесь не нужна, а сервис и точка отказа добавляются.
- Сейчас очередь в каталогах `pending/running/done` под замком. Она переживает падение, её видно
  `ls`, и она уже работает.
- Когда появится SQLite (п. 3), очередь стоит перенести таблицей в ту же БД. Тогда постановка задачи
  и изменение проекта пойдут одной транзакцией: исчезнет класс ошибок «сцену поставили,
  а проект не обновился» (вариант C2 из финального ревью волны 1).
- Диспетчер GPU остаётся отдельным systemd-сервисом на хосте: он владеет движками и `generation.lock`.

### 5. Процессы и тесты
- **Процессы.** Web и worker разнести на два контейнера в compose вместо двух процессов
  в `entrypoint.sh`: у каждого свой healthcheck и рестарт.
- **Тесты UI.** Playwright на собранном клиенте и настоящем сервере с фейковыми движками
  вместо фейкового DOM в Node. Приёмочный сценарий задачи 13 волны 1.5 — готовая основа
  для первого e2e-теста.
- **Логи.** Структурные JSON-логи web и worker рядом с `events.jsonl` диспетчера, чтобы отчёт
  о прогоне (`tools/battle_report.py`) читал одно место.

## Не менять
- Протокол LLM — OpenAI-совместимый (CAILA, Qwen, OpenRouter); выбор модели — волна 1.6.
- Диспетчер GPU на хосте (systemd), движки на хосте, панель в Docker.
- Медиа на диске в `/home/alex/Outputs/h3-panel`.
