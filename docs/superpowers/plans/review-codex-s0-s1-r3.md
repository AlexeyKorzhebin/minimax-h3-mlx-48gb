**Новые проблемы и незакрытые последствия правок**

1. **Блокер — новый L6 падает на разветвлении источников; API может вернуть ошибку уже после сохранения.**  
   **Место:** П:4020–4035, 4073–4076; 5635–5638, 5659; 5738–5740.

   Допустимый вход: `s2 → s1` и `s3 → s1`, герой присутствует во всех трёх сценах. `_chain(project, s3)` поднимается к `s1`, затем выбирает только первого потомка — `s2`. В полученной цепочке нет `s3`; обращение `described[scene.id]` даёт **`KeyError: 's3'`**. Это воспроизведено выполнением кода линтера из плана.

   O8 допускает такой источник. Линтер вызывается после выхода из `db.tx`, поэтому по коду операции изменение уже зафиксировано, когда построение ответа падает. Аналогичный порядок есть в O7.

   **Предложение:** определить обход ветвей с обязательным включением проверяемой сцены; добавить случаи разветвления и циклического источника. Нужен также API-тест, проверяющий ответ и повторное чтение после такой правки. Ограничивать источники только непосредственным предшественником без изменения спеки нельзя.

2. **Блокер — ответ сохранения уничтожает текст, введённый во время запроса.**  
   **Место:** П:7275–7282, 7352, 7391.

   Сценарий: пользователь отправил `mine-v1`, пока PATCH выполняется — дописал `mine-v2`. Ответ содержит `mine-v1`, после чего новый `setDraft(fromScene(result.scene))` безусловно заменяет текущий ввод. Поля доступны во время запроса, состояния `saving` нет.

   Выполнение извлечённого тела `save` с задержанным ответом подтвердило результат: черновик снова равен `mine-v1`, основание тоже равно `mine-v1`; новая правка потеряна и карточка считается чистой. Это касается и «Сохранить моё» после 409. Тесты используют немедленные ответы и этого не проверяют.

   **Предложение:** либо блокировать редактирование на время сохранения, либо учитывать изменения после отправки и сохранять их отдельным черновиком. Добавить тест с управляемым Promise: отправка → новый ввод → ответ → проверка актуального поля и следующего PATCH.

3. **Важно — L2 и L6 всё ещё проверяют другое содержание.**  
   **Место:** П:3962–3984, 4045–4076; С:849, 853.

   Воспроизведённые результаты:

   | Вход | Результат | Расхождение |
   |---|---|---|
   | `Wind rustles through reeds without music.` | L2 | Положительный источник есть; `without` делает отрицательным всё утверждение. |
   | `No music. This scene is indoors.` | Нет L2 | Описание места ошибочно принято за источник звука. |
   | В первой сцене `a woman with a loose dark braid walks.`, во второй та же фраза с `sits.` | L6 во второй | Портрет одинаков; отличается действие. |

   `_names_a_source` по-прежнему принимает практически любое содержательное слово. `_hero_description` сравнивает целые предложения вместе с действием.

   **Предложение:** отделить отрицание от положительного источника внутри утверждения; для L6 отделить портретную часть от действия. Добавить эти случаи в независимые ожидания. Если предполагается более узкая эвристика, явно согласовать её границы вместо заявления полного соответствия L2/L6.

4. **Важно — `SameOriginGuard` проверяет только authority и допускает необработанную ошибку разбора.**  
   **Место:** П:1598–1625; тесты П:1445–1515.

   При `Host: alex-neuro:8766`, схеме запроса `http` и отсутствии `Sec-Fetch-Site` выполнение middleware из плана дало:

   - `Origin: https://alex-neuro:8766` → пропуск;
   - `Origin: //alex-neuro:8766` → пропуск;
   - `Origin: http://[` → необработанный `ValueError`.

   Origin определяется **схемой, хостом и портом**, а не одним `netloc`. Это подтверждает [документация MDN](https://developer.mozilla.org/en-US/docs/Web/Security/Defenses/Same-origin_policy#definition_of_an_origin). Разбор URL также не заменяет валидацию входа — см. [документацию Python](https://docs.python.org/3/library/urllib.parse.html#url-parsing-security).

   **Предложение:** проверять допустимый формат Origin и нормализованную тройку; повреждённые значения отклонять контролируемым ответом. Добавить тесты другой схемы, `null`, повреждённого Origin и `Sec-Fetch-Site: same-site`. Последнего сейчас нет: расширение разрешённого списка до `same-site` существующие случаи не обнаружат.

   Сам порядок **TrustedHost → guard → BodyLimit** корректен. Обхода Host allow-list в рассмотренном коде не обнаружила.

5. **Важно — проверка секретов путает «не найдено» с «проверить не удалось».**  
   **Место:** П:3396–3401.

   Любой ненулевой результат `docker run … grep` ведёт к сообщению `no planted secret in the image`. Это включает ошибку запуска контейнера и ошибку чтения файлов самим `grep`. `set -e` внутри условия `if` не спасает.

   Воспроизведено со стабом `docker`, возвращающим 125: скрипт печатает успех и заканчивается кодом 0.

   **Предложение:** отдельно обработать 0 — утечка, 1 — секрет не найден, остальные коды — ошибка проверки с ненулевым завершением. Добавить отрицательные тесты запуска и чтения. Фактическую утечку рабочего ключа не установила; дефект именно в доказательстве безопасности образа.

6. **Важно — часть новых мутационных доказательств снова проверяет форму.**  
   **Место:** П:3208–3215, 3281–3292, 3576; 6002–6005, 6108–6114, 6272.

   У отката стаб возвращает один `STUB_IMAGE` для любого `inspect`, а команда `docker image inspect … latest` вообще не поддерживается и завершается кодом 3. Поэтому предложенная мутация краснеет из-за неизвестной команды, ещё до проверки выбора между A и B. Отдельное сравнение argv закрепляет способ вызова, но фактического восстановления A тест не моделирует.

   У версии промпта исправлен тест самой `prompt_version()`. Однако замена **места использования** на `"prompt_version": "bdfb247d800c"` в П:6272 остаётся незакрытой: интеграционный тест ожидает именно эту константу, а тест другого файла вызывает только функцию хеша.

   **Предложение:** для отката моделировать отдельно работающий образ A, `latest=B`, таблицу тегов и результат восстановления. Для промпта — подменить файл, выполнить O25 и проверить версию в сохранённом `proposal.llm_json`.

7. **Важно — мобильная панель и Playwright не покрывают завершение текущей правки.**  
   **Место:** П:7294–7297, 7383–7385; 6839–6877.

   После 409 карточка снимает своё действие с панели. На телефоне снизу появляется, например, «Предложить сцены» или «Применить», а «Сохранить моё» остаётся внутри карточки. Основное действие текущей правки снова не закреплено.

   Playwright проверяет положение «Сохранить героя», «Сохранить сцену» и «Применить», но не нажимает их. В маршрутах теста даже нет соответствующих сохранений. Подмена мобильного обработчика сохранения сцены на пустую функцию этими проверками не обнаруживается.

   **Предложение:** определить действие панели при конфликте; добавить мобильные нажатия с точной проверкой тела запроса и результата. Для сохранения сцены нужен также случай нескольких изменённых карточек, чтобы проверить выбор адресата действия.

8. **Важно — исправление SQLite обоснованно, но регрессия отмены чтения не закреплена тестом.**  
   **Место:** П:36, 1313–1331, 1774–1788, 1890–1900.

   Открытие и закрытие соединения внутри одного вызова рабочего потока устраняет описанную гонку владения соединением. Нового нарушения И10 здесь не вижу.

   Однако существующий SSE-тест проверяет последовательность событий; он не удерживает чтение активным во время отключения клиента. «25 прогонов без падения» не обеспечивает обнаружение возврата прежнего опасного закрытия.

   **Предложение:** добавить детерминированный тест с барьером внутри чтения: отключить клиент, проверить, что соединение ещё не закрыто, разрешить завершение чтения и проверить закрытие после него. Мутация преждевременного закрытия должна давать assertion, без необходимости добиваться настоящего segfault.

9. **Мелочь — новые Playwright-заглушки нарушают собственное правило точной маршрутизации.**  
   **Место:** П:67 против П:2332 и 6830.

   `startsWith("GET /api/studio/events?")` принимает любую строку запроса, включая неверный `after`. Это не мешает проверке геометрии, но противоречит явно установленному ограничению.

   **Предложение:** задать точный ожидаемый маршрут либо отдельно проверить параметры. **Можно исправить в ходе реализации.**

Проверка :8765 стала существенно надёжнее: прямых команд изменения старой панели в процедуре не обнаружила. Оставшийся дефект доказательства отката относится к студии, а не к установленному повреждению :8765.
