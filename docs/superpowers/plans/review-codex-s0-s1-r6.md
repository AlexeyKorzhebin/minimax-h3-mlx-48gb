**Блокер — сохранённые данные владельца перезаписываются без разрешения конфликта.**

Причина находится в [проверке `expected_revision` и вычислении прироста ревизии](/Users/aleksey.korzhebin/Yandex.Disk.localized/Projects/minimax-h3-mlx-48gb/docs/superpowers/plans/2026-10-21-studio-s0-s1.md:6020), а контракт закреплён в [И1](/Users/aleksey.korzhebin/Yandex.Disk.localized/Projects/minimax-h3-mlx-48gb/docs/superpowers/specs/2026-10-10-studio-part1-core-design.md:490).

Воспроизвела извлечённым клиентским модулем, затем извлечённым `update_scene` с SQLite `:memory:`:

1. Обе вкладки открыли `requested_s=8`, `revision=1`.
2. Вкладка A вводит `8.2`.
3. Вкладка B сохраняет `8.1`. Сервер оставляет `revision=1`: кадры остаются `192`.
4. Даже доставленный A снимок B не вызывает устаревания: ревизия равна базе, грязное поле продолжает показывать `8.2`.
5. Обычное «Сохранить» A отправляет `{expected_revision: 1, requested_s: 8.2}`.
6. Сервер принимает запрос. Повторное чтение БД: **`8.2`, ревизия 1**. Конфликта и выбора «Сохранить моё» не было.

**Да, это потеря данных владельца на сервере.** Одинаковое число кадров не делает сохранённые `requested_s` одинаковыми. Более того, воспроизвела аналогичное затирание `state_in_text`: оно тоже сохраняется без повышения ревизии. Текущий [серверный тест прямо закрепляет такое поведение](/Users/aleksey.korzhebin/Yandex.Disk.localized/Projects/minimax-h3-mlx-48gb/docs/superpowers/plans/2026-10-21-studio-s0-s1.md:5701).

Предлагаемое исправление спеки и плана:

- Сохранить `revision` для отпечатка генерации; добавить **`edit_version` для всех сохраняемых редактируемых полей**, включая `requested_s`, `state_in_text`, `state_out_text` и референсы. Повышать при фактическом изменении, атомарно с записью.
- В §7 задать обязательный `expected_edit_version` для O8 и ответ 409 при несовпадении. `state_version` оставить для одобрений.
- Добавить версию в схему, ответы и события; в задаче 12 использовать её для базы черновика, упорядочивания снимков и разрешения конфликтов. Охватить также записи существующих сцен через O7/O26 соответствующими предусловиями.
- Добавить серверную регрессию двух вкладок: второй устаревший PATCH получает 409, повторное чтение сохраняет `8.1`; перезапись возможна после явного выбора с актуальной версией. Фейковый сервер должен воспроизводить этот контракт.

Это требует исправления **спеки и плана до реализации**, а не только клиентской функции.
