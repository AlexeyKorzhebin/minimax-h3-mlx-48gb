**Повтор контрпримера r6**

На извлечённом `update_scene` и SQLite `:memory:`:

1. Обе вкладки читают `requested_s=8`, `revision=1`, `edit_version=0`.
2. A готовит `8.2`; B сохраняет `8.1`.
3. Получается `frames=192`, `revision=1`, **`edit_version=1`**.
4. A отправляет `{expected_edit_version: 0, requested_s: 8.2}` → **409**. Повторное чтение сохраняет **8.1**.
5. С актуальной версией 1 перезапись принимается, версия становится 2.

Для `state_in_text` результат аналогичен: значение B сохраняется, устаревший A получает 409. На клиенте снимок B сохраняет грязное `8.2`, не повышает базу черновика и приводит к конфликту при сохранении. Задержанный снимок исходного `8` уже не откатывает сохранённое `8.1`.

**Блокер — удаление обходит защиту правок**

В [коде O7](/Users/aleksey.korzhebin/Yandex.Disk.localized/Projects/minimax-h3-mlx-48gb/docs/superpowers/plans/2026-10-21-studio-s0-s1.md:6186) проверяются только сцены, **оставленные в массиве**. Удаляемые сцены получают `deleted_at` без проверки версии.

Подтверждённая последовательность:

1. A и B читают проект версии 2 со сценами S и T, обе версии правок — 0.
2. A готовит удаление S.
3. B сохраняет в S новый `state_in_text` через O8 → версия S становится 1, версия проекта остаётся 2.
4. A отправляет O7: `expected_revision=2`, массив содержит только T с версией 0.
5. **O7 успешно выполняется.** S вместе с новой правкой исчезает из рабочего проекта; последующий O8 для S возвращает **404**.

Физически текст остаётся в удалённой строке БД — это **логическая потеря доступных владельцу данных**, а не уничтожение байтов. Штатного восстановления здесь нет.

[R29](/Users/aleksey.korzhebin/Yandex.Disk.localized/Projects/minimax-h3-mlx-48gb/docs/superpowers/plans/2026-10-21-studio-s0-s1.md:193) явно объявляет удаление намерением вкладки, но намерение удалить прочитанную версию не проверяет конфликт с последующей сохранённой правкой. **O26 воспроизводит ту же проблему**, заменяя старые сцены через `replace_scenes`.

До реализации нужны предусловия и для удаляемых сцен — например, отдельный список `{scene_id, expected_edit_version}`, проверяемый в той же транзакции. O26 должен передавать соответствующие версии заменяемого набора.
