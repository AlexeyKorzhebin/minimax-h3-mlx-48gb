# Веб-морда для h3: очередь, работник, страница

**Дата:** 2026-08-11
**Состояние:** переработано после ревью codex, готово к плану

## Зачем

Сейчас прогон ставится shell-скриптом: скопировать прошлый, поправить параметры, не забыть
`caffeinate`, не забыть трекер памяти, положить лог не в `/tmp`. Каждый из этих пунктов уже был
забыт хотя бы раз, и каждый стоил либо ночи, либо потерянных данных. Страница убирает этот класс
ошибок: параметры вводятся в форму, всё остальное делается всегда и одинаково.

Главный сценарий — **ночная очередь**: перед сном накидать несколько задач, перечитать их, что-то
поправить, что-то поднять наверх, и утром увидеть результаты. Из него следует почти всё
нетривиальное в этой спеке.

Четыре вещи, которые страница должна уметь в итоге, в порядке приоритета:

1. **Ставить прогоны** — первая волна, эта спека.
2. **Показывать, что считается** — прогресс и превью-кадры.
3. **Сравнивать готовое** — галерея роликов рядом с их параметрами.
4. **Вести журнал экспериментов** — что пробовали и что вышло.

Волны 2–4 ложатся поверх без переделки и в эту спеку не входят.

## На чём строим

Проверено 2026-08-11 на реальных файлах, а не по памяти:

- **`h3_48gb/runs.py` не импортирует MLX.** Он написан как «основа для будущей веб-страницы» и
  читает состояние прогонов прямо из чекпойнтов.
- **`h3_48gb/cli.py` тоже не импортирует MLX при импорте модуля** — но **`spec_from_args()` может
  его втянуть**: при `--image` без явного канваса вызывается `resolve_canvas`, а он импортирует
  `minimax_h3_mlx.packing`, который импортирует `mlx.core`. Поэтому сервер **не** вызывает
  `spec_from_args` у себя; см. «Проверка задачи».
- **`h3 generate` продолжает подходящий чекпойнт автоматически** (`run_generate(..., resume=True)`);
  `--restart` существует именно чтобы этого избежать.
- **`runs._writer_alive` возвращает три состояния**: занято, свободно, не могу знать. Но замок,
  который он пробует, принадлежит *диффузии*, а не задаче целиком, — см. «Аренда задачи».
- **`ERROR_CODES` содержит 24 записи.** Эта спека добавляет шесть.
- **Имя выходных файлов — `h3-{tag}-{W}x{H}`**, сида в нём нет. Отсюда требование к тегам ниже.

## Глобальные ограничения

Обязательны для всех задач плана:

- **Сервер слушает только `127.0.0.1`.** Ни авторизации, ни TLS, ни доступа из сети — и ничего из
  этого не должно появиться «на всякий случай».
- **Ни одной новой зависимости.** Сервер на `http.server` из стандартной библиотеки. У проекта
  шесть зависимостей, и это его свойство, а не случайность.
- **Серверный процесс никогда не импортирует `mlx`,** ни при загрузке модуля, ни при обработке
  запроса. Проверяется тестом, который импортирует `h3_48gb.web`, прогоняет через него постановку
  задачи с `--image` и убеждается, что `mlx` не появился в `sys.modules`.
- **`caffeinate -dimsu` оборачивает каждую задачу, а не работника.** Работник простаивает сутками;
  запрещать машине спать всё это время неправильно. Спать нельзя ровно во время прогона.
- **Логи не в `/tmp`.** Лог задачи лежит по неизменному пути `queue/logs/<id>.log` и никуда не
  переезжает вместе с задачей: перенести два файла атомарно нельзя, а половина переноса хуже, чем
  его отсутствие.
- **Все подтверждённые записи durable:** временный файл → `fsync(файл)` → `os.replace` →
  `fsync(каталог)`. То же, что уже делает `CheckpointStore.write`, и по той же причине: после
  внезапной перезагрузки подтверждённая задача обязана существовать целиком или не существовать
  вовсе.
- **Промпты остаются файлами в `prompts/` и попадают в git.** Сравнение имеет смысл только при
  побайтово одинаковом промпте.
- **Единственный формат обмена — JSON**, включая ошибки: `{"ok": false, "error": {"code",
  "message", "detail"}}`, как уже делает CLI.

## Очередь

Каталог `<H3_OUTDIR>/queue/`:

```
queue/
  queue.lock          общий замок на изменения состояния
  worker.lock         замок единственного работника
  pending/  running/  done/  failed/     задачи, по одному JSON
  leases/<id>.lock    аренда идущей задачи, держится работником
  results/<id>.json   отметка о результате, пишется до отпускания аренды
  prompts/<id>.txt    снимок промпта, с которым задача поставлена
  logs/<id>.log       вывод задачи, неизменный путь
```

**Переход состояния — переименование файла между каталогами.** В пределах одной файловой системы
`os.rename` атомарен, и `ls pending/` отвечает на вопрос «что в очереди» без разбора JSON.

**Но переименования недостаточно.** Правка ждущей задачи читает файл, а потом пишет его обратно — и
между этими двумя действиями работник может задачу забрать. Тогда `os.replace(temp, pending/<id>)`
не упадёт, а **создаст файл заново** в каталоге, из которого его только что забрали: задача
окажется одновременно в `running/` со старыми параметрами и в `pending/` с новыми, и выполнится
дважды. По той же причине последовательный обход четырёх каталогов не является снимком — задачу
можно увидеть и в `pending/`, и в `running/`, если перенос случился между чтением каталогов.

Поэтому есть **замок очереди** `queue/queue.lock`:

- `submit`, `claim`, `update`, `move_to_front`, `cancel`, `finish`, `reconcile` берут его
  эксклюзивно (`LOCK_EX`);
- `scan` берёт разделяемо (`LOCK_SH`) на весь обход;
- держится **только на файловых операциях**, миллисекунды, и никогда — на время работы прогона.
  Замок очереди и запуск подпроцесса не пересекаются.

### Файл задачи

Имя: `<YYYYmmdd-HHMMSS>-<tag>-<xxxx>.json`, где `tag` — тег задачи, приведённый к `[a-z0-9-]`, а
`xxxx` — четыре случайных символа. Создание — через `O_CREAT|O_EXCL`, при столкновении суффикс
берётся заново. Одной метки времени и тега мало: две постановки в одну секунду с одним тегом дали
бы один `id`, и `os.replace` молча уничтожил бы одну из задач.

```json
{
  "id": "20260811-130500-centaur-15s-a3f9",
  "created_at": "2026-08-11T13:05:00",
  "args": ["generate", "--prompt-file", "<queue>/prompts/20260811-130500-centaur-15s-a3f9.txt",
           "--mode", "t2va", "--width", "896", "--height", "576",
           "--duration", "15", "--steps", "8", "--seed", "20260815",
           "--tag", "centaur-15s", "--outdir", "/Users/…/19-пятнадцать-секунд"],
  "prompt_source": "prompts/centaur-battle.txt",
  "prompt_sha256": "9f2c…",
  "output_stem": "/Users/…/19-пятнадцать-секунд/h3-centaur-15s-896x576",
  "note": "проверка потолка памяти на пятнадцати секундах",
  "estimate": {"forwards": 7, "seconds": 7819, "peak_gb": 35.7},
  "priority": 0,
  "started_at": null,
  "finished_at": null,
  "exit_code": null,
  "log_tail": null
}
```

`args` — список строк ровно в том виде, в каком его принимает `h3`. Это и есть контракт: работник
исполняет их без единого преобразования, потерять при переводе нечего, потому что перевода нет.

**Снимок промпта.** `--prompt-file` в задаче указывает **не** на файл в `prompts/`, а на его копию в
`queue/prompts/<id>.txt`, сделанную при постановке. Иначе правка промпта через страницу между
постановкой и запуском привела бы к тому, что прогон выполнит не те байты, которые человек
проверял, — прямое нарушение того самого принципа, ради которого промпты вообще лежат в файлах.
`prompt_source` и `prompt_sha256` сохраняют, откуда снимок взят, чтобы отчёт мог это назвать.

**`output_stem`** вычисляется при постановке по формуле CLI (`outdir / f"h3-{tag}-{W}x{H}"`) и
хранится в задаче. Он нужен дважды: чтобы отказать в постановке при столкновении и чтобы понять,
завершилась ли задача, когда работника убили (см. «Сверка при старте»).

**Тег обязателен и уникален.** Сида в имени выходного файла нет, поэтому три сида одной сцены с
одним тегом пишут в один и тот же `.mp4`, `.wav`, `.npz` и `.json`, и последний затирает остальные.
`submit` и `update` отказывают кодом `output_stem_conflict`, если такой `output_stem` уже занят
ждущей или идущей задачей либо существующим на диске файлом. Форма подставляет сид в тег по
умолчанию (`centaur-15s-s20260815`), но не запрещает это переписать.

### Что умеет `queue.py`

```python
def submit(root, args, note, estimate, prompt_source, prompt_text) -> Job   # → pending/
def claim(root) -> Job | None                                               # pending/ → running/
def finish(root, job_id, exit_code, log_tail) -> Job                        # running/ → done|failed
def update(root, job_id, args, note, estimate, prompt_source, prompt_text) -> Job
def move_to_front(root, job_id) -> Job
def cancel(root, job_id) -> Job
def scan(root) -> tuple[list[Job], list[Broken]]                            # под LOCK_SH
def reconcile(root) -> list[Job]                                            # см. «Сверка при старте»
```

`update`, `move_to_front` и `cancel` работают **только** внутри `pending/`, под эксклюзивным замком
очереди, и поднимают `JobNotPending`, если задача из него ушла. Идущую задачу страница не трогает:
отменить её означало бы убить процесс, а решение убить двухчасовой прогон принимается руками.

`update` сохраняет `id`, `created_at` и `priority`; заменяет `args`, `note`, `estimate` и снимок
промпта. Изменение тега **не** переименовывает файл: `id` — ссылка, по которой лежат лог, снимок и
аренда.

`move_to_front` вместо общего изменения приоритета: страница умеет ровно это, и лишней операции в
контракте быть не должно. Ставит `priority` на единицу больше максимума среди ждущих. Порядок
выборки — `(-priority, id)`.

`scan` возвращает **две** коллекции: разобранные задачи и нечитаемые файлы с причиной. Битую задачу
нельзя просто пропустить — она станет невидимой, а человек будет гадать, почему очередь короче, чем
он помнит. Тот же инвариант уже есть у `runs.scan`.

## Работник

`h3 worker` — цикл, который держит машину занятой ровно одной задачей за раз.

**Один на машину.** При старте берёт `flock(LOCK_EX|LOCK_NB)` на `queue/worker.lock` и держит его
до конца. Второй работник получает `worker_already_running` и завершается — не молча.

### Аренда задачи

Замок чекпойнта **не годится** как признак того, что задача жива, и это надо сказать прямо, потому
что первая версия этой спеки так и предполагала. Чекпойнт удаляется сразу после диффузии, замок
отпускается — и только потом CLI пишет `.npz`, `.mp4`, `.wav` и отчёт. Сверка, попавшая в это окно,
увидела бы «свободно», вернула бы почти готовую задачу в очередь, и повторный прогон затёр бы
результат. Есть и окно в начале: подпроцесс уже запущен, а файла замка ещё нет.

Поэтому у задачи своя **аренда**: `queue/leases/<id>.lock`, `flock(LOCK_EX)`, который **работник
берёт до запуска подпроцесса и отпускает после его завершения**. Аренда живёт ровно столько, сколько
живёт `caffeinate … h3 generate`, и умирает вместе с работником, если того убили. Замок чекпойнта
остаётся тем, чем и был, — признаком того, что идёт диффузия, и его читает страница для прогресса.

**Отметка о результате** `queue/results/<id>.json` (`{"exit_code": N, "finished_at": "..."}`)
пишется durable-протоколом сразу после выхода подпроцесса и **до** отпускания аренды.

### Сверка при старте

Работник владеет единственным замком работника, значит ни одна задача из `running/` не исполняется
им. Для каждой такой задачи:

| аренда | отметка | `output_stem`.mp4 | что делает работник |
|---|---|---|---|
| занята | — | — | задача жива, оставить в `running/` **и не брать новых, пока она не кончится** |
| свободна | есть | — | завершить по коду из отметки: в `done/` или `failed/` |
| свободна | нет | есть | считать сделанной: отметку потеряли уже после успеха, `done/` с пометкой |
| свободна | нет | нет | вернуть в `pending/` — прогон оборвался, он продолжится со своего чекпойнта |

Третья строка нужна из-за окна между выходом подпроцесса и записью отметки. Готовый `.mp4`
существует только после полного успеха, поэтому его наличие — надёжнее любого таймаута.

Строка про занятую аренду важна отдельно: **живая чужая задача запрещает брать следующую.** Иначе
работник запустил бы второй процесс на 36 ГБ, и оба ушли бы в своп.

### Цикл

Пока не попросили остановиться: под замком очереди взять первую задачу из `pending/`; если пусто —
спать 5 секунд. Иначе перенести в `running/`, записать `started_at`, взять аренду и запустить

```
caffeinate -dimsu <sys.executable> -m h3_48gb <args…>
```

в **отдельной группе процессов** (`start_new_session=True`), направив stdout и stderr в
`queue/logs/<id>.log`. Дождаться выхода. Записать отметку, отпустить аренду, записать
`finished_at`, `exit_code` и последние 40 строк лога в `log_tail`, перенести в `done/` при коде 0 и
в `failed/` иначе.

**Остановка.** Первый `SIGTERM` или `SIGINT`: текущей задаче дать доработать (это часы, но
прерывать её без нужды хуже), новых не брать, затем отпустить замки. Второй `SIGTERM`: послать
сигнал **всей группе процессов**, а не одному `caffeinate`, — иначе вложенный Python останется
сиротой без аренды и без работника. Задача остаётся в `running/` и будет разобрана сверкой при
следующем старте.

## Сервер

`h3 web [--port 8765]`. Слушает `127.0.0.1`, печатает адрес и работает, пока его не остановят.

| метод и путь | что делает |
|---|---|
| `GET /` | страница |
| `GET /static/<файл>` | HTML, JS, CSS из `h3_48gb/webui/` |
| `GET /api/state` | всё состояние одним ответом: очередь, прогоны, жив ли работник |
| `POST /api/jobs` | поставить задачу: `{"args": [...], "note": "...", "prompt_source": "..."}` |
| `PUT /api/jobs/<id>` | заменить содержимое ждущей задачи; та же проверка, что при постановке |
| `POST /api/jobs/<id>/top` | поднять ждущую задачу в начало очереди |
| `DELETE /api/jobs/<id>` | убрать задачу из `pending/` |
| `POST /api/estimate` | оценка стоимости по `args`, без постановки |
| `GET /api/prompts` | список файлов `prompts/*.txt` с размерами |
| `GET /api/prompts/<имя>` | содержимое |
| `PUT /api/prompts/<имя>` | сохранить содержимое |
| `GET /media/<прогон>/<файл>` | превью-кадр или готовый ролик из каталога прогона |

`GET /api/state`:

```json
{"ok": true,
 "worker": {"state": "alive"},
 "queue": {"pending": [...], "running": [...], "done": [...], "failed": [...],
           "broken": [{"path": "...", "error": "..."}]},
 "runs": [ … то, что отдаёт runs.scan() … ]}
```

`worker.state` — одно из `alive`, `stopped`, `unknown`, по пробе `flock` на `queue/worker.lock`.
PID не отдаётся: замок его не сообщает, а выдумывать поле, которое нечем заполнить, нельзя. Если
работник не запущен, страница обязана сказать это прямо, а не делать вид, что задача вот-вот пойдёт.

### Проверка задачи

Сервер **не вызывает** `spec_from_args` у себя — тот при `--image` без явного канваса втягивает
MLX. Вместо этого проверка делается подпроцессом:

```
<sys.executable> -m h3_48gb generate --dry-run --json <args…>
```

Новый флаг `--dry-run` у `generate`: собрать `RunSpec`, применить все проверки, напечатать отчёт
о том, что было бы запущено, и выйти, не загрузив ни одного веса. Отсюда три выгоды сразу:

- правила проверки существуют **в одном экземпляре**, а не в двух похожих;
- MLX живёт в подпроцессе, а серверный процесс остаётся чистым по построению, а не по обещанию;
- `argparse` при неизвестном флаге поднимает `SystemExit(2)`, а не `CliError`, и в общем процессе
  прошёл бы мимо `except Exception`; здесь это просто код возврата 2, который сервер переводит в
  400 с кодом `args_invalid` и текстом из stderr.

Код возврата 0 — задача годится; отличный от нуля — 400 с телом, которое напечатал CLI. Проверка
занимает доли секунды и происходит только при постановке и правке, не при каждом нажатии клавиши:
оценка стоимости — чистая формула и считается на сервере.

**Разрешена только подкоманда `generate`.** После разбора сервер проверяет `namespace.command ==
"generate"` и отказывает кодом `command_not_allowed` иначе — иначе через API можно было бы поставить
задачей `worker` или `web` и получить вложенного работника. `--no-checkpoint` для задач очереди
запрещён тем же кодом: без чекпойнта прерванная задача теряет часы, а очередь на том и стоит, что
прерванное продолжается.

### Пути

Каждый путь из запроса приводится к абсолютному и проверяется по `Path.resolve()` — не по тексту,
чтобы `..` и символические ссылки не проходили. Корней **три**:

| корень | что там | доступ |
|---|---|---|
| корень репозитория | промпты, код | чтение и запись в `prompts/` |
| `H3_OUTDIR` | выход, очередь | чтение и запись |
| `~/models` (или `H3_MODELS_ROOT`) | веса, LoRA, таблицы AdaLN | **только чтение** |

Третий корень обязателен: чекпойнт по умолчанию — `~/models/h3-converted`, и правило из двух корней
отвергло бы значение по умолчанию собственного CLI.

Проверяются **все** флаги, содержащие путь, а не только очевидные: `--prompt-file`, `--outdir`,
`--image`, `--end-image`, `--checkpoint`, `--checkpoint-dir`, `--preview-stem`, `--adaln-cache`,
`--turbo-lora`. `--checkpoint-dir` и `--preview-stem` пишут на диск и опаснее прочих. Список флагов
берётся из парсера, а не переписывается руками, чтобы новый флаг с путём не оказался незамеченным.

`/static/` и `/media/` проверяются тем же `resolve` **после** декодирования URL. Имена промптов
обязаны соответствовать `[A-Za-z0-9_-]+\.txt`.

Localhost — не оправдание для обхода каталогов: браузер выполняет чужой JavaScript, и запрос к
серверу может прийти не только со своей страницы.

## Оценка стоимости

Считается на сервере по подогнанной модели из `docs/RESULTS.md`:

```
rows      = (5.53 + 1.641*(sec − 2.4)) * (W/16) * (H/16) + 81*sec + 820
s_forward = 5.699e-3 * rows + 2.671e-7 * rows²
forwards  = steps − 1
diffusion = s_forward * forwards
overhead  = 36 + 7.44e-5 * W * H * sec   # загрузка весов, кодирование, декод, сборка mp4
seconds   = diffusion + overhead
peak_gb   = 9.3 * rows / 37657 + (22.1 если DiT восьмибитный иначе 12.1)
```

Константа 820 — замеренный вклад текстовых строк; 37657 строк ≈ 9.3 ГБ активаций — оттуда же.
Разрядность DiT читается из `quant_config.json` чекпойнта.

**Показывать надо полное время, а не время диффузии.** Формула проходов считает только диффузию, а
человек ждёт весь прогон: загрузку весов, кодирование текста, декодирование видео и звука, сборку
mp4. Накладные замерены на четырёх прогонах 2026-08-11 и растут почти линейно по объёму
`W·H·sec` — то есть по работе видео-VAE, а не по времени диффузии:

| канвас, длительность | диффузия | всего | накладные |
|---|---|---|---|
| 448×288, 10 с | 11.1 мин | 13.3 | 2.2 |
| 448×288, 10 с (второй сид) | 10.9 | 13.1 | 2.2 |
| 896×576, 10 с | 65.5 | 72.3 | 6.8 |
| 896×576, 15 с | 138.6 | 148.8 | 10.2 |

Подгонка `36 + 7.44e-5·W·H·sec` секунд воспроизводит все четыре точки в пределах 0.2 минуты.
Постоянное слагаемое в 600 секунд, стоявшее здесь раньше, завышало черновик на 448×288 вдвое —
и это ровно тот случай, когда грубая константа хуже отсутствия оценки: черновик задуман как
одиннадцатиминутный, и обещание в двадцать одну минуту меняло бы решение человека.

**Точность самой формулы на этой точке — 6.3%, а не 3%.** Предсказание 1117 с на проход против
замеренных в среднем 1187.7. Причём проходы дрейфовали вверх по ходу прогона (1086, 1161, 1105,
1180, 1347, 1252, 1183) при росте свопа с 7.9 до 10.4 ГБ — то есть часть расхождения не в модели, а
в состоянии машины. Оценке в форме можно верить с точностью «плюс-минус десять процентов», и
формулировать её надо соответственно: «≈2 ч 30 мин», а не «2 ч 28 мин».

Пик памяти предсказан в 35.7 ГБ, замерен в 33 — модель завысила на 8%, то есть ошибается в
безопасную сторону.

**Порог — предупреждение, а не запрет.** Выше 40 ГБ страница показывает предсказанный пик рядом с
физическими 48; выше 46 ГБ требует явной галочки «всё равно поставить». Запрещать по экстраполяции
неправильно — модель подогнана на одном канвасе. Молчать тоже нельзя: 15 секунд на 1248×832 просят
49 ГБ.

## Страница

Один экран, три части сверху вниз.

**Форма.** Промпт, канвас, длительность, шаги, сид, тег, чекпойнт, LoRA и её сила, режим, заметка.
Значения по умолчанию — те же, что у CLI. Под кнопкой оценка: «≈2 ч 10 мин, пик ~36 ГБ из 48»,
пересчитывается при изменении полей запросом к `/api/estimate`.

**Форма не очищается после постановки.** Главный сценарий — накидать несколько задач на ночь: одна
сцена с разными сидами, один рецепт с двумя длительностями. Очищенная форма заставляла бы вводить
всё заново ради одного поля. После успешной постановки поля остаются, а сид и тег обновляются на
следующие.

Поля «сколько сидов» нет: серия ставится тремя нажатиями по неочищенной форме, а показывать три
ролика рядом всё равно негде до волны сравнения.

**Редактор промпта.** Обычное текстовое поле со всем текстом — чужой промпт можно вставить целиком.
Страница разбирает его на лету и подсказывает:

- подсвечивает блоки `[a.b-c.ds]`, `Characters:`, `overall_soundscape:`, `non_diegetic_music:`;
- складывает тайминги блоков и сравнивает с `--duration`, показывая расхождение;
- отмечает разрывы и перехлёсты между соседними блоками;
- говорит, если нет `overall_soundscape` или `non_diegetic_music` — у режима `t2va` без них
  пропадает звук.

Разбор **ничего не переписывает**. Он показывает, что видит, и оставляет решение человеку: формат
задан моделью, а не нами, и правило, которого мы не знаем, не должно превращаться в запрет.

Сохранение — в `prompts/<имя>.txt` через `PUT`. Коммитить в git страница не пытается: тихий коммит
из браузера — худший способ узнать, что твоя история изменилась.

**Очередь и прогоны.** Строка состояния работника. Что идёт сейчас: шаг, доля, ETA, миниатюра
превью. Что ждёт — с тремя действиями у каждой задачи: править, наверх, удалить. У идущих и
завершённых действий нет — не серые кнопки, а их отсутствие: серая кнопка обещает, что когда-нибудь
нажмётся. Что закончилось за сутки — с кодом возврата и видимой причиной падения. Отдельной
строкой — нечитаемые файлы очереди, если они есть.

Рядом со ждущими — сумма их оценок и время окончания в формате «четыре задачи, ≈8 ч 04 мин, до
08:48», посчитанные той же формулой, что и отдельные оценки. Это и есть ответ на вопрос, ради
которого набирается ночная очередь.

Опрос `/api/state` раз в 20 секунд: шаг длится десять-восемнадцать минут, обслуживать реальное
время нечего.

## Дизайн

Сделан скиллом `huashu-design`. **Утверждённый макет с подставными данными —
`~/Research/TestVideo/_макеты/h3-panel-light.html`** (плюс `h3-panel-light.css` и
`h3-panel-light.js`): та же раскладка из трёх файлов, что требует спека, без сети и без сборки.
Реализация повторяет его; решения записаны здесь текстом, чтобы не зависеть от того, открыт ли
макет.

**Визуальный язык — светлый и воздушный, в духе системных приложений macOS.** Содержимое лежит
белыми карточками со скруглением 14 px на подложке `#f1f2f5`, с полупиксельной обводкой и едва
заметной тенью: карточки плавают над фоном, как в системных настройках. Первая версия макета была
плотной приборной панелью на сплошной сетке линий, со скруглением 2–3 px, капслоком в заголовках и
моноширинным шрифтом во всём подряд — этот набор читался как девяностые и заменён целиком. Плотность
информации при этом сохранена: данных на экране столько же, они разведены воздухом, а не сокращены.

**Ритм по восьмёрке:** поле страницы 28 px, поле карточки 22 px, шаг между карточками 24 px, между
группами параметров 22 px. Группы разделяет пространство; волосяная линия осталась только между
однотипными строками списка и вдвинута под колонку имени.

**Липкая верхняя строка** — полупрозрачная панель с размытием, под ней проезжает содержимое. Держит
состояние работника и текущий прогресс: главный вопрос «идёт ли и когда кончится» задаётся по
десять раз за день мимоходом и не должен уезжать вверх, пока человек возится с формой.

**Форма в две колонки:** слева промпт с разбором, самый широкий элемент страницы; справа параметры
тремя группами, разделёнными пространством.

**Одна колоночная сетка на все три списка очереди** — ждущие, идущие, завершённые — при одинаковых
внутренних полях карточек. Тогда время и память сравниваются взглядом по вертикали, в том числе
между ждущей задачей и уже посчитанной. Числовые колонки выровнены вправо.

**Четыре состояния различаются формой знака, а не цветом:** кольцо — ждёт, залитая точка с
пульсирующим ореолом — идёт, галочка в круге — сделано, крестик в круге плюс мягкая красная
подложка строки — упало. Страница читается в чёрно-белой печати и при дальтонизме.

**Прогресс — делениями по числу проходов, а не процентом.** Проходов семь или девятнадцать, и «три
из семи» считывается быстрее, чем «43%».

**Память — шкала 0–48 с рисками на 40 и 46,** повторённая микроверсией в каждой ждущей строке:
кандидаты сравниваются между собой, а не только с порогом.

**Шрифт один — системный (`-apple-system`), из сети ничего не грузится.** Числа набраны им же с
`font-variant-numeric: tabular-nums`, поэтому колонки сходятся по вертикали без моноширинного.
Моноширинный оставлен там, где он честно работает: пути, идентификаторы, имена файлов, текст
промпта и текст ошибки. Иерархия по размеру и весу, не капсом: раздел 17/600, заголовок карточки
15–16/600, тело 13, вторичный текст 12–12.5 серым. Мельче 12 px на странице нет.

**Цвет.** Единственный акцент — системный синий (`#007aff`, в тексте `#0062d6`). Сигнальные цвета —
пастельная заливка с тёмной обводкой текста: зелёный «сделано», оранжевый «внимание по памяти»,
красный «упало». Ни градиентов, ни цветов сверх этих.

**Тёмная тема — парная, а не инверсия:** подложка `#101114` темнее карточек `#1c1e22` по той же
логике «содержимое над фоном», контраст мягче, тени заменены обводкой, сигнальные цвета светлее и
приглушённее. Переключение по системной настройке.

**Элементы управления в системном духе:** поля с мягкой заливкой без рамки, рамка и кольцо
появляются на фокусе; списки со своей стрелкой; галочка «всё равно поставить» — настоящий
переключатель.

**Движение только служебное:** пульс текущего шага и идущей задачи, 120–180 мс на фокус и
наведение, всё выключается при `prefers-reduced-motion`.

Отклонённые направления лежат в `_макеты/` и `_макеты/варианты/` — первая приборная версия,
функциональный брутализм на волосяных линиях и панель в духе Брауна. Из последней взята микрошкала
памяти в строках очереди.

## Ошибки

| ситуация | ответ |
|---|---|
| `--dry-run` вернул ненулевой код | 400, тело от CLI; при коде 2 — `args_invalid` с текстом stderr |
| подкоманда не `generate`, либо `--no-checkpoint` | 400, `command_not_allowed` |
| выходное имя уже занято | 400, `output_stem_conflict`, с занятым `output_stem` в `detail` |
| путь вне трёх корней или запись в корень моделей | 400, `path_outside_root` |
| имя промпта с разделителем пути | 400, `prompt_name_invalid` |
| задача уже не в `pending/` при правке, поднятии или отмене | 409, `job_not_pending` |
| каталог очереди недоступен на запись | 500, `queue_unwritable`, с путём в `detail` |
| второй работник | выход с `worker_already_running` |
| неожиданное исключение | 500, `internal_error` с типом в `detail`, как в CLI |

Шесть новых кодов (`args_invalid`, `command_not_allowed`, `output_stem_conflict`,
`path_outside_root`, `prompt_name_invalid`, `job_not_pending`) плюс `worker_already_running`
добавляются в `ERROR_CODES`: контракт один на CLI, работника и сервер, а не три похожих.

Сервер не имеет права уронить очередь: он кладёт файлы в `pending/` и читает состояние.

## Тестирование

`tests/test_queue.py` — переходы состояний: постановка, захват, завершение по обоим кодам, правка,
поднятие и отмена только из `pending/`, порядок выборки при десяти задачах с близкими метками и при
заданных приоритетах, столкновение `id` при двух постановках в одну секунду с одним тегом, отказ по
`output_stem_conflict`, нечитаемый файл виден как `Broken`, а не пропадает.

`tests/test_worker.py` — с подставной командой вместо `h3 generate`: код 0 ведёт в `done/`,
ненулевой в `failed/`, `log_tail` содержит последние строки, второй работник отказывается стартовать,
первый `SIGTERM` не прерывает задачу, второй доходит **до настоящего внука** через группу процессов
(проверяется реальным дочерним процессом, а не подставным `caffeinate`), `caffeinate` присутствует в
командной строке.

`tests/test_web.py` — запросами к экземпляру на случайном порту: каждый маршрут; отказ формы даёт
код CLI; `worker`, `web` и `--no-checkpoint` отклоняются; путь через `..` и через символическую
ссылку отклоняется для каждого флага с путём; `/media` и `/static` не выпускают за свои корни после
URL-декодирования; `/api/state` показывает работника мёртвым, когда его нет. Плюс тест, что
постановка задачи с `--image` не вносит `mlx` в `sys.modules` серверного процесса.

**Восстановление проверяется впрыском отказа**, а не только последовательными переходами. Для
каждой точки — постановка, захват, запуск, выход подпроцесса, запись отметки, финальное
переименование — тест обрывает работника ровно там и проверяет, что следующая сверка приводит
очередь в правильное состояние по таблице из «Сверки при старте». Все четыре её строки покрыты, в
том числе «отметки нет, а `.mp4` есть».

**Гонки проверяются гонками.** Правка, поднятие и отмена вызываются в момент, когда работник уже
взял задачу, — с настоящей параллельностью (поток или процесс), а не последовательно: тест
«сначала `claim`, потом `update`» проверяет только то, что и так очевидно.

**Дисциплина.** Для каждого теста, покрывающего замки, сверку и переходы состояний: удалить или
инвертировать строку, которую он защищает, убедиться в красноте, вернуть строку. Текст ошибки,
выданной на мутации, попадает в отчёт задачи. За неделю до этой спеки так нашлись четырнадцать
пустых проверок; все четырнадцать читались нормально, и ни одна не была найдена чтением. Для
тестов формы и разметки правило не обязательно — там цена ошибки несопоставима.

## Чего здесь нет

Авторизации, доступа из сети, многопользовательности, отмены идущей задачи, серии сидов одной
кнопкой, галереи сравнения, журнала экспериментов, коммита промптов в git из браузера.

Волны 2–4 не требуют переделки: наблюдение — тот же `/api/state` плюс превью-кадры, которые
пайплайн уже пишет; сравнение и журнал строятся на отчётах прогонов, которые с 2026-08-10
записывают промпт, режим, чекпойнт, LoRA, силу и число проходов.
