# Диалоговый редактор промпта в веб-морде

**Дата:** 2026-08-12. **Ветка:** `h3-web`. **Статус:** согласовано в брейншторме, ждёт плана.

## Зачем

Официальный сервис MiniMax прогоняет короткий пользовательский запрос через закрытый
LLM-улучшитель H3-Context-IR, разворачивающий его в полную структуру промпта. Локально этого
слоя нет — отсюда часть разрыва в качестве. Закрываем его чатом с локальной моделью прямо в
веб-морде: окно промпта, рядом диалог, который этот промпт правит. Claude в контуре не участвует.

## Решения, принятые в брейншторме

| вопрос | решение |
|---|---|
| где живёт | модалка в существующей веб-морде, не отдельная страница и не отдельный сервис |
| кто разговаривает | пользователь ↔ локальная модель через `llama-server`; Claude не участвует |
| раскладка | адаптивная: на широком экране диалог сбоку от промпта (промпт всегда виден — правки заметны глазами), на узком — снизу |
| правка руками | окно промпта в модалке редактируемо: мелочь правится пальцами, модель не дёргается |
| протокол | OpenAI-совместимый `/v1/chat/completions`; ответ модели — строго JSON по схеме (`response_format: json_schema`) |
| провайдеры | абстракция в `provider.py`: `llama-local` сейчас, `openai`-совместимые внешние — той же записью конфига; их может быть несколько |
| токены | только в `.env` (права 600, в `.gitignore`); у каждого провайдера своя переменная, `providers.json` хранит лишь её имя |
| память | «очередь главнее»: работник гасит `llama-server` перед задачей, но **спросив пользователя**; чат поднимает модель обратно, когда GPU свободен |
| источники промпта | три: пустой лист, промпт из библиотеки, промпт ждущей задачи — редактировать существующее так же, как создавать новое; в данных сессии зарезервирован четвёртый вид источника `clip` (ролик проекта) — поведение появится со спекой «проекты» |
| режим с кейфреймом | сессия несёт `mode` и путь кадра; для i2v модель обязана выдать дословную первую строку (поле `instruction` схемы), а сам кадр **прикладывается к ходу картинкой** — Qwen-пресет зрячий (mmproj), llama.cpp принимает изображения в том же OpenAI-протоколе; модель пишет якорь Shot 1 с реального кадра, не со слов |
| разрешения | пресеты черновик/малое/большое + ручной ввод остаётся |
| очередь | плюс дублирование любой задачи в один клик |
| обвязка | скрипты старта и останова веб-морды (сервер + работник) |
| системный промпт | файл-документация формата в репе (выжимка руководств MiniMax), версионируется git |

## Архитектура

Три новых куска поверх существующих `web.py` / `app.js` / `queue.py`:

```
h3_48gb/provider.py      абстракция LLM-провайдера + жизненный цикл llama-server
h3_48gb/web.py           маршруты /api/chat/*, /api/providers, подтверждение выгрузки
h3_48gb/webui/app.js     модалка: окно промпта + лента диалога + статус модели
docs/h3-prompt-system.md системный промпт: документация формата для LLM
```

### provider.py

Конфиг `<outdir>/providers.json` (не секретный):

```json
{
  "active": "qwen-local",
  "providers": {
    "qwen-local": {
      "type": "llama-local",
      "llama_server": "/opt/homebrew/bin/llama-server",
      "presets_ini": "~/models/presets.ini",
      "preset": "Qwen3.6-35B-A3B-Uncensored-HauhauCS-Aggressive-Q6_K_P",
      "port": 8080,
      "ctx": 49152,
      "resident_gb": 31,
      "temperature": 0.7
    },
    "gemma-local":  { "type": "llama-local", "preset": "gemma-4-26B-uncensored-heretic-Q8_0" },
    "openrouter":   { "type": "openai", "base_url": "https://openrouter.ai/api/v1",
                      "model": "…", "api_key_env": "OPENROUTER_API_KEY" }
  }
}
```

Секреты — `<outdir>/.env`, построчно `ИМЯ=значение`, права 600, файл в `.gitignore`.
Читается при старте сервера; `api_key_env` в конфиге называет переменную, значение в
`providers.json` не попадает никогда. Внешних провайдеров и токенов может быть несколько.

Интерфейс провайдера один: `chat(messages, json_schema) -> dict`, плюс для `llama-local`
`ensure_up()` / `shutdown()` / `status()`. Оба типа ходят по одному OpenAI-протоколу —
различие только в том, кто поднимает процесс. `llama-local` поднимает `llama-server` тем же
образом, что `~/models/restart-llama.sh` (`--models-dir`, `--models-preset`, `--models-max 1`,
health-check `/health`, лог в файл), и выбирает пресет из `presets.ini`.

### Протокол хода диалога

Каждый ход — один stateless-запрос (историю несёт клиент, модель между запросами ничего не
помнит, поэтому выгрузка модели ничего не теряет):

```
system:  docs/h3-prompt-system.md + текущий текст промпта + параметры (режим, длительность)
messages: история диалога этой сессии
response_format: json_schema →
{
  "reply": "строка — ответ пользователю в чате",
  "prompt": {
    "instruction": "строка | null — I2VA/FLF-строка, если режим с кейфреймом",
    "integrated_multimodal_description": "строка",
    "overall_soundscape": "строка",
    "non_diegetic_music": "строка"
  } | null
}
```

`prompt: null` — реплика без правки (уточняющий вопрос, обсуждение). Непустой `prompt`
собирается в текст на клиенте (поля фиксированы схемой — модель не может потерять поле или
сломать порядок), кладётся в окно промпта и тут же проходит существующий живой разбор
(`analysePrompt`), подсветку и таймлайн-полоску — они переезжают в модалку как есть.

История сессии — `<outdir>/chat/<id>.json` (история + текущий промпт + источник);
переживает перезагрузку страницы и выгрузку модели.

### Память: «очередь главнее», но с подтверждением

- Работник хочет взять задачу, а `llama-local` поднят → задача получает статус
  «ждёт выгрузки LLM», страница показывает подтверждение: «Выгрузить модель и начать
  генерацию?». Да → `shutdown()`, работник стартует. Нет → задача ждёт, модель живёт.
- Сообщение в чат при идущей генерации → модель не поднимается; в ленте плашка
  «идёт прогон, LLM поднимется после него (~N мин)» с оценкой из прогресса работника.
  Сообщение остаётся в поле ввода, ничего не теряется.
- Сообщение в чат при свободном GPU и незапущенной модели → `ensure_up()` со статусом
  «поднимаю модель…» (30–60 с на 30 ГБ), затем обычный ход.
- Внешние провайдеры (`type: openai`) память не занимают и в этих правилах не участвуют.

### Модалка

Открывается из трёх мест, кнопка завершения зависит от источника:

| источник | вход | кнопка завершения |
|---|---|---|
| форма постановки | «Новый через диалог» | «в Редактор» — текст в редактор формы, дальше обычная постановка |
| библиотека промптов | «обсудить» у промпта | «сохранить промпт» (PUT /api/prompts/<имя>) |
| ждущая задача | «обсудить» у задачи | «обновить задачу» (PUT /api/jobs/<id>) |

Внутри: окно промпта (редактируемое руками, с разбором и таймлайном), лента диалога с полем
ввода, выпадашка провайдера, статус модели (не поднята / поднимаю… / готова / GPU занят
прогоном). Раскладка адаптивная: при достаточной ширине диалог сбоку от промпта, обе колонки
видны одновременно; на узком экране — колонкой, промпт сверху.

**Сценарий импорта чужого промпта.** Найденный в интернете промпт — целиком по спецификации,
частично похожий или в чужом формате — вставляется руками прямо в окно промпта (оно
редактируемое, отдельной кнопки импорта не нужно). Живой разбор немедленно показывает, что
в нём не по стандарту. Команда в чате («проверь», «переформатируй», «приведи к стандарту»)
уходит модели вместе с текущим текстом окна; ответ обязан прийти строгим JSON по схеме —
переформатирование в наш стандарт гарантировано конструкцией, а не дисциплиной модели.
Дальше обычные итерации: «замени такой-то блок на такой-то». Системный промпт-документация
явно оговаривает: при переформатировании содержание сохраняется, меняется только разметка;
придумывать новое — только по прямой просьбе.

### Пресеты разрешений и дублирование

В форме постановки — три кнопки-пресета, заполняющие ширину/высоту (ручной ввод остаётся):

| пресет | канвас | стоимость 10 с, 8 шагов |
|---|---|---|
| черновик | 448×288 | ~13 мин |
| малое | 896×576 | ~77 мин |
| большое | 1344×768 | ~218 мин |

У каждой задачи (ждущей и законченной) — действие «копия»: новая ждущая задача с теми же
промптом и параметрами.

### Скрипты обвязки

`scripts/web-start.sh` — сервер + работник под `caffeinate -dimsu`, логи в
`~/Research/TestVideo/_логи/`, идемпотентен (повторный запуск не плодит процессы).
`scripts/web-stop.sh` — останавливает работника (текущая задача дописывает чекпойнт шага и
прерывается — resume её продолжит), гасит `llama-server` и веб-сервер.

## Обработка ошибок

- llama-server не поднялся за 60 с → плашка в чате с хвостом его лога, модель считается
  не поднятой, сообщение остаётся в поле ввода.
- Модель вернула невалидный JSON (внешний провайдер без поддержки схемы) → один повтор с
  напоминанием схемы в system; второй провал → плашка «модель не удержала формат», сырой
  текст показывается в ленте как обычная реплика без правки промпта.
- Переменная из `api_key_env` не найдена в `.env` → провайдер виден в выпадашке серым с
  подписью «нет токена».
- Обрыв соединения со страницей во время хода → сессия в `<outdir>/chat/` цела, повторное
  открытие модалки продолжает с места обрыва.

## Тесты

В духе репозитория: JS через настоящий node (`_node_eval`), Python — против настоящих
маршрутов, каждый тест наблюдается красным (мутационная проверка).

- Сборка текста промпта из JSON-ответа; `prompt: null` не трогает окно; правка руками не
  затирается следующим ходом (модель получает текущий текст, не свой прошлый).
- Маршруты `/api/chat/*`: сессии, ходы, источники, кнопки завершения по источнику.
- `llama-local` с фейковым llama-server (`http.server`-мок): ensure_up / shutdown / status,
  health-check, выбор пресета.
- Правило «очередь главнее»: задача при поднятой модели → «ждёт выгрузки LLM», подтверждение
  → shutdown → старт; отказ → модель живёт.
- Ход чата при идущей генерации не поднимает модель.
- `.env`: ключ читается по имени из конфига, в `providers.json` и в ответах API секретов нет.
- Дублирование задачи; пресеты разрешений заполняют поля.
- Импорт: текст, вставленный в окно руками, уходит модели как текущий промпт следующим ходом
  (проверяется на моке по телу запроса); документация-системный промпт содержит правило
  «при переформатировании содержание сохраняется».

## Вне рамок

- Реализация конкретных внешних провайдеров (абстракция и конфиг готовы, включение — задача
  на потом: добавить запись в `providers.json` и токен в `.env`).
- UI управления провайдерами (правятся файлом).
- Потоковая передача ответа (streaming) — ответ приходит целиком; при желании добавится позже.
- **Проекты** — сценарий из N роликов, автокейфреймы из предпоследней секунды, автосклейка,
  чат в контексте ролика сценария (как баллада, но руками страницы). Отдельная спека и план
  сразу после этого; здесь только задел — вид источника `clip` в данных сессии.

## Принятые отклонения

Ревью всей ветки (2026-08-13) нашло два места, где реализация разошлась с тем, что можно было бы
прочитать в спеке выше буквально. Оба разбора — не баги, а сознательный выбор попроще; код не
трогается, здесь только запись решения.

- **`bad_model_json` после повтора приземляется плашкой в ленте (`{role: "note", kind: "bad"}`),
  а не репликой ассистента.** `provider.chat` обрезает сырой ответ модели до первых 400 символов
  (`raw2[:400]`) прежде чем завернуть его в `ProviderError`; страница показывает эту строку через
  `chatFailureText` → `landFailure`. Полноценная реплика потребовала бы притворяться, что модель
  ответила по формату, когда она как раз не удержала формат — плашка честнее.
- **Таймаут подъёма `llama-server` — 90 секунд, а не 60** (`provider.LlamaLocal.ensure_up`,
  `timeout: float = 90.0`). Живой smoke на холодной модели (раздел «Реализовано» ниже) показал,
  что 60 с местами не хватало на macOS с диска Time Machine; 90 с — наблюдаемый запас, а не
  цифра из спеки.
