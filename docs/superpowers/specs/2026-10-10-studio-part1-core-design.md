## 1. Цель и критерий готовности

**Цель части 1.** Ядро студии и минимальный мастер, с которыми владелец сам, без ssh/curl/правки
файлов, проходит путь «идея → две сцены → первый кадр → эскизы → выбор → финал → сборка → mp4», где
исполнитель подключён по договору (§8), состояние живёт в одной базе, задачи переживают обрывы, а
мастер и любой MCP-хост работают через один и тот же набор явных операций (§7).

**Критерий готовности (один).** Владелец в браузере на Маке открывает мастер студии
`http://alex-neuro:8766/studio` и без подсказок проходит путь выше на **настоящем ComfyUI** alex-neuro
(H3 fl2va/ref2va и Krea 2): две сцены (1 — от кадра Krea 2 или от референса, 2 — продолжение от
последнего кадра 1), эскизы обеих, выбор, финалы обеих, повторное одобрение продолжения, сборка,
скачивание mp4. Проход журналируется (что нажато, сколько ждал, где застрял). Путь закреплён
сквозным тестом (§12.3) на имитациях; тот же контрактный тест исполнителя (§12.2) зелёный на живом
ComfyUI alex-neuro. Тест доказывает, что путь есть; проход владельца — что им можно пользоваться.

Срезы §14 — каждый со своей приёмкой владельцем; критерий достигается в S4, часть сделана после S6.
Режим «Картинка» (§19, срез S2b) — отдельный путь со своей приёмкой; в критерий §1 не входит и его
не задерживает.

### 4.4. Минимальный мастер (S0–S4)

`h3_48gb/studio/web/` — React + Vite + TypeScript (STACK §2), собирается в статику, отдаётся

почти чёрный текст, линии 1px без теней, единственный акцент — кобальт; заголовки Inter Tight, текст

под кадром; карточки проектов в две колонки с превью 16:9. Темы: светлая (главная), тёмная, «как в
системе». Запрещено: кремовые/бежевые фоны, терракотовый/оранжевый акцент, serif-заголовки
(узнаваемый стиль Anthropic), вид shadcn по умолчанию. Телефон 390 px: одна колонка, главная кнопка

### 6.2. Длительность и снимок входов дубля

**Длительность (Codex-13, проверено кодом).** Сетка `frames = 17n+5` (`sglang_args.py:81`), FPS 24.
8 с = 192 кадра — уже на сетке; пример редакции 1 «197» был ошибкой. 15 с = 360 → `grid_frames_up`
даёт 362 = 15,083 с, это выше `MAX_SECONDS`, и старый `parse()` такой длительности не примет
(`:166`, `:170-177`); 3 с = 72 → 73 = 3,042 с. Правило студии: `requested_s` хранится как ввёл
человек/сценарист; `frames` = ближайшая точка сетки к `requested_s × 24`, при равенстве — вверх,
затем зажим в `[73, 345]` (3,042–14,375 с). Фактическая длительность = `frames / 24` — её показывают
мастер и план. Граница 345 — для обоих исполнителей, пока §15 п.1 не покажет, что ComfyUI держит больше.

Канонический JSON (ключи отсортированы, `ensure_ascii=False`), `inputs_sha256` — хеш этой строки:

```json
{"executor":"comfy","template":{"id":"h3-fl2va","sha256":"…"},"tier":"sketch","steps":20,"seed":12,
 "prompt":"<prompt_final дословно>","requested_s":8.0,"frames":192,"canvas":[896,512],
 "keyframes":[{"position":0,"asset_id":"a_…","sha256":"…","upstream_take_id":"t_…"}],
 "refs":[{"ord":1,"role":"person","asset_id":"a_…","sha256":"…","label":"<Picture 1>"}],
 "audio":[],"scene_revision":3,"engine_version":"ComfyUI v0.42.0 b1a247c9"}
```

Два дубля с одинаковым `inputs_sha256` — «пересъёмка с тем же сидом»: разрешена, мастер предупреждает.

## 7. API явных операций

Все под `/api/studio`. Тело ошибки — `{"error":{"code","message","detail"}}` (DRAFT (а)), свой
обработчик `RequestValidationError` → 400 `args_invalid`; проверки «проект есть» — зависимостями до
разбора тела. Одни и те же операции вызывают мастер (§4.4) и MCP (§11).

Версии и ключи:
- **`expected_revision`** проекта — для операций над его содержимым и составом сцен (O4, O5, O7,
  O26). Не совпало → 409 `revision_conflict`, `detail.current` — снимок.
- **`expected_edit_version`** сцены (И1a) — для правки сцены: O8 и каждая сцена с `scene_id` в O7
  (у новой сцены его нет). Не совпало → 409 `revision_conflict`, `detail.current` — сцена (в O7 ещё
  `detail.scene_id`). Конфликт правок по `revision` не решается: И1 не растит её на `requested_s`
  с теми же кадрами и на `state_in_text`/`state_out_text`. Для O7 версия — на каждой сцене, а не
  общий счётчик проекта: O8 проект не трогает (ниже), иначе правка одной сцены ломала бы чужой O7.
  **Удаление — тоже правка:** O7 и O26 несут `deleted: [{scene_id, expected_edit_version}]` — сцены,
  которые вкладка убирает, с прочитанной версией; живая сцена ни среди оставленных, ни среди
  удаляемых → 409 (молчание о сцене — не согласие на удаление), удаляемая со старой версией → 409
  с `detail {scene_id, current}`. Проверка — в той же транзакции.
- **`expected_state_version`** — для одобрения (O16). Не совпало → 409 `state_conflict`.
- **Правила роста.** `project.revision` +1: O4, O5, O7, O26 (структура и состав сцен). Сцена:
  `revision` +1 по И1; `edit_version` +1 по И1a; `state_version` +1 при одобрении, снятии одобрения,
  смене `review_state`.
  O8 и O16 проект не трогают — поэтому правка одной сцены не делает устаревшим план другой.
- **План (O10)** запоминает `revision` и `state_version` каждой сцены плана и каждой сцены-источника
  кадра; O11 сверяет их, не `project.revision`; расхождение → 409 `plan_stale` с перечнем.
- **`Idempotency-Key`** (заголовок, обязателен для O11, O12, O15, O19, O24, O30): `OP_LOG` хранит sha256 тела
  и ответ 24 ч; тот же ключ + другое тело → 422 `idempotency_mismatch`. Мастер генерирует `uuid4` на
  нажатие; MCP — из `(tool, plan_id)`.

### 8.1. Протокол (`h3_48gb/studio/executors/base.py`)

```python
class Capabilities(TypedDict):
    find: Literal["exact", "none"]          # можно ли найти нашу задачу без engine_ref
    restart_evidence: bool                  # может ли сказать, что процесс перезапущен после момента t
    progress: bool                          # (шаг, всего) во время работы
    cancel: Literal["hard", "soft", "none"] # hard — останавливает вычисление; soft — только убирает результат
    async_submit: bool                      # submit возвращает ref быстро, работа идёт отдельно

class Probe(TypedDict):
    alive: bool
    ready: bool            # шаблон/модели spec доступны и чужих задач нет
    detail: str
    missing: list[str]     # ред. 3: файлы моделей шаблона, которых нет в GET /models/<folder>;
                           # непустой → задача сразу failed «модель не установлена», без ожидания 600 с

class EngineStatus(TypedDict):
    state: Literal["queued", "running", "done", "failed", "cancelled", "lost"]
    progress: tuple[int, int] | None
    error: str | None

class Executor(Protocol):
    name: str
    capabilities: Capabilities
    def gpu_scope(self, spec: TaskSpec) -> str: ...
    def probe(self, spec: TaskSpec) -> Probe: ...           # Codex-9: readiness зависит от spec
    def estimate_s(self, spec: TaskSpec) -> float: ...
    def submit(self, spec: TaskSpec) -> str: ...            # engine_ref; spec.task_id передаётся движку
    def find(self, spec: TaskSpec) -> str | None: ...       # только при capabilities.find == "exact"
    def restarted_since(self, t: float) -> bool | None: ... # только при restart_evidence
    def status(self, ref: str) -> EngineStatus: ...
    def result(self, ref: str, dest: Path) -> list[Path]: ...
    def cancel(self, ref: str) -> None: ...
```

`TaskSpec` — Pydantic-модель из материализованного `inputs_json` плюс `task_id`, `dest_dir`.
Исполнитель не читает БД и не знает про сцены.

**Контрактный тест проверяет каждую заявленную возможность и только её** (Codex-9): `find` — если
`exact`; `progress` монотонен — если `True`; после `cancel` при `hard` статус `cancelled` и движок
свободен, при `soft` — результат не забирается. Адаптер с `find="none"` обязан проходить сценарий
`submit_unknown → ручное разрешение` (§8.5).

Readiness ≠ liveness: `alive=True, ready=False` → `waiting_ready` с `wait_reason` из `detail`, опрос
каждые 5 с до 600 с (`start_timeout` ComfyUI в диспетчере, `dispatcher.py:83`), потом `failed`.

### 8.5. Жизненный цикл задачи и дубля

```mermaid
stateDiagram-v2
  [*] --> blocked : O11, дубль pending_input (ждёт кадр предыдущей сцены)
  [*] --> queued : O11 / O12 без зависимостей
  blocked --> queued : зависимость done → материализация inputs_json (И2, И3)
  blocked --> cancelled : зависимость failed / cancelled → upstream_failed
  queued --> waiting_gpu : воркер взял
  waiting_gpu --> waiting_gpu : acquire → wait / starting / wait_qwen (30 с, 5 с при starting)
  waiting_gpu --> waiting_ready : acquire → ready
  waiting_ready --> waiting_ready : probe.ready=false (5 с, ≤600 с)
  waiting_ready --> submitting : probe.ready=true, submit_attempt_at записан
  submitting --> running : engine_ref записан (И9)
  submitting --> submit_unknown : таймаут / обрыв без ответа
  submit_unknown --> running : find нашёл (только find=exact)
  submit_unknown --> queued : find=None и restarted_since(submit_attempt_at)=True, attempts+1 ≤ 2
  submit_unknown --> submit_unknown : иначе — ждёт человека (O27)
  submit_unknown --> queued : O27 resubmit (риск дубля показан)
  submit_unknown --> cancelled : O27 cancel
  running --> running : status → progress
  running --> downloading : status.done
  running --> failed : status.failed (текст движка)
  running --> lost : status.lost
  lost --> queued : attempts<2 (один автоповтор)
  lost --> failed : второй раз
  downloading --> verifying : файлы на диске
  verifying --> succeeded : кадры, sha256, asset, TAKE done или stale (И4), каскад И11
  verifying --> failed : кадры залиты / файл пуст / число кадров ≠ frames
  queued --> cancelled : O14
  waiting_gpu --> cancelled : O14
  waiting_ready --> cancelled : O14
  running --> cancelling : O14 → executor.cancel
  cancelling --> cancelled : status.cancelled или 30 с (engine_stop=unconfirmed)
  failed --> [*]
  succeeded --> [*]
  cancelled --> [*]
```

**`submit_unknown` (Codex-4, принято).** Автоматический повтор без положительной находки разрешён в
одном случае: движок доказуемо перезапущен после попытки постановки (`restarted_since`), а `find` не
нашёл ни записи, ни файлов — задача не могла выжить в процессе, которого больше нет. Во всех
остальных случаях задача ждёт человека: мастер показывает «Не знаю, принял ли ComfyUI задачу» и две
кнопки (O27). Правило «GPU util < 10 % 60 с» удалено: низкая загрузка совместима с задачей, которая
ждёт в очереди, качает входы или уже завершилась.

**Логическая и фактическая отмена (Codex-9).** O14 пишет `cancel_requested_at` — это логическая
отмена: результат такой задачи никогда не крепится к дублю, даже если придёт. Фактическая —
`executor.cancel` у `running`; без подтверждения за 30 с задача `cancelled` с
`engine_stop=unconfirmed`, и следующая GPU-задача ждёт, пока `probe.ready` (очередь движка пуста).
Отмена в `submit_unknown` — логическая; если `find` позже найдёт задачу, воркер вызовет `cancel`.

Таблица `reconcile` при старте воркера (перенос `queue.py:1161-1250`, тесты точным равенством):

| `status` в БД | `engine_ref` | Действие |
|---|---|---|
| `running` / `cancelling` | есть | продолжить опрос / отмену |
| `submitting` | нет | `submit_unknown` → один вызов `find` и `restarted_since` по правилу выше |
| `submit_unknown` | нет | то же; без находки остаётся `submit_unknown` (не теряется после падения воркера) |
| `downloading` / `verifying` | есть | повторить скачивание/проверку |
| `waiting_gpu` / `waiting_ready` | нет | `queued` |
| `blocked` | — | проверить зависимость: `done` → материализовать; `failed/cancelled` → `cancelled` |
| любой с `cancel_requested_at` и без `engine_ref` | — | `cancelled` |

## 9. Режиссёр

Два пути, одна целевая форма — сцены O7 с полями `action/performance/sound/music, mode, requested_s,
state_in/out, refs`. **Основной — свой «Сценарист»; ai-writer — дополнительный** (решение владельца 4).

### 9.1. «Идея → сцены»: LLM-роль «Сценарист» (`studio/director/scenarist.py`) — основной путь

Как Scenario mode старой панели (`docs/h3-prompt-system.md:232` «Scenario mode: a multi-scene video
project», схема `provider.PROMPT_SCHEMA` `:32`, ветка `project.scenes`), но со своей строгой схемой
`STUDIO_SCENES_SCHEMA` и через `provider.chat` (`:937`):

- вход: идея, число сцен (в мастере части 1 — 2), формат кадра, кастинг (тег, EN-описание,
  `portrait_phrase`), `style_block` проекта;
- выход LLM на сцену: `action`, `performance` (состояние, его смена, мимика, взгляд, руки —
  PROMPT-FORMAT «Вывод для спеки»), `sound` (материал + контакт + что не звучит, GAIT-SOUND),
  `music`, `state_in`, `state_out`, `cast_tags`, `requested_s` в пределах 3–15;
- **код считает арифметику**: число сцен, снап длительности (§6.2), режимы по правилу CJM этап 4 —
  первая сцена с героем → `refs` (или `from_frame`, если владелец сделает кадр), каждая следующая →
  `from_frame` с `prev_last_frame`; дословная `portrait_phrase` вклеивается кодом, не LLM;
- системный промпт — `studio/director/prompts/scenarist.md`, версия пишется в `proposal.llm_json`;
- результат — `proposal` (переживает рестарт API), применяется O26 через тот же путь, что O7.

Шаблон кадра Krea 2 — `director/keyframe_prompt.py`: `style_block` + `portrait_phrase` + `state_in`
сцены + кадрирование («medium shot, eye level»), без звука; размер по формату: 16:9 → 1344×768,
9:16 → 768×1344 (кратно 64; 1344×768 замерен, GPU-DAY п.2).

### 9.2. «Глава → клип»: ai-writer, дополнительный путь (S7, вне критерия)

Для сложных сцен владелец пишет клип-сценарий в ai-writer и импортирует его: O24 по `clip_id`

`duration` → `requested_s` со снапом §6.2 (5–10 с AW укладываются в 3,042–14,375). Тест: импорт

### 19.3. Данные

**Решение: картинки живут в проекте `kind='image'`.**

| Вариант | За | Против | Итог |
|---|---|---|---|
| **Проект с `kind='image'`** | `task.project_id`, фильтр SSE по проекту, снимок O3, список O1, каталог `projects/<id>/`, `Idempotency-Key` уже есть (план S2–S3 R-S2-1); владелец видит работу над картинкой как именованный, возвращаемый проект; `asset` глобален (у таблицы нет `project_id`), поэтому вариант идёт в любую сцену и в кастинг любого видеопроекта существующими O8/O5 | у проекта есть поля видео (`frame_format`, сцены): нужна изоляция видов (И18) | **принято** |
| Отдельная сущность `image_board` | чистая модель без полей видео | второй список, второй снимок, свой фильтр событий, `task.project_id` пришлось бы делать nullable или дублировать; два понятия «проект» у владельца | отвергнут |
| Картинки внутри видеопроекта (вкладка) | нет нового вида | владелец просил путь **без видео**; картинка до видеопроекта (сначала кадр, потом решаю, в какой ролик) некуда положить | отвергнут |

**Миграция `004_images.sql`** (после 002 `scene_source_auto` из S1 и 003 связей задач S2; `PRAGMA user_version = 4`):

```sql
ALTER TABLE project ADD COLUMN kind TEXT NOT NULL DEFAULT 'video'
  CHECK (kind IN ('video', 'image'));

CREATE TABLE image_draft (
  project_id TEXT PRIMARY KEY REFERENCES project(id),
  edit_version INTEGER NOT NULL DEFAULT 0,
  idea_text TEXT NOT NULL DEFAULT '',
  prompt_ru TEXT NOT NULL DEFAULT '',      -- то, что правит владелец (§17.1 п.11 в)
  prompt_en TEXT NOT NULL DEFAULT '',      -- то, что уходит в модель; виден и правится
  prompt_en_state TEXT NOT NULL DEFAULT 'none'
    CHECK (prompt_en_state IN ('none', 'fresh', 'stale', 'owner')),
    -- fresh: перевод текущего prompt_ru; stale: prompt_ru правили после перевода (LI8);
    -- owner: английский правлен руками (следующая правка prompt_ru снова делает stale)
  prompt_ru_version INTEGER NOT NULL DEFAULT 0,  -- +1 на правку prompt_ru; перевод помнит, с какой снят
  prompt_llm_json TEXT,                    -- модель, версия промпта роли, сырой ответ (как proposal.llm_json)
  template TEXT NOT NULL,                  -- id шаблона картинки (§8.2)
  profile TEXT,                            -- профиль карточки (Qwen: 'fast' | 'full'); NULL у моделей без профилей
  width INTEGER NOT NULL, height INTEGER NOT NULL,
  steps INTEGER,                           -- NULL = card.limits.steps_default
  seed_mode TEXT NOT NULL DEFAULT 'auto' CHECK (seed_mode IN ('auto', 'manual')),
  seed INTEGER,
  count INTEGER NOT NULL CHECK (count BETWEEN 1 AND 8),
  updated_at TEXT NOT NULL,
  CHECK (seed_mode = 'auto' OR seed IS NOT NULL)
);

CREATE TABLE image_batch (
  id TEXT PRIMARY KEY,
  project_id TEXT NOT NULL REFERENCES project(id),
  ord INTEGER NOT NULL,                    -- № партии в проекте, с 1
  draft_edit_version INTEGER NOT NULL,     -- версия черновика, из которой собран план
  template TEXT NOT NULL, template_sha256 TEXT NOT NULL, profile TEXT,
  prompt_ru TEXT NOT NULL,                 -- для показа у партии; в модель не идёт и во входы не входит
  seed_mode TEXT NOT NULL, count INTEGER NOT NULL,
  repeat_of_variant_id TEXT REFERENCES image_variant(id),
  plan_id TEXT NOT NULL,
  created_at TEXT NOT NULL,
  UNIQUE (project_id, ord)
);

CREATE TABLE image_variant (
  id TEXT PRIMARY KEY,
  batch_id TEXT NOT NULL REFERENCES image_batch(id),
  ord INTEGER NOT NULL,
  seed INTEGER NOT NULL,                   -- И13
  inputs_json TEXT NOT NULL,               -- И14, канонический JSON ниже
  inputs_sha256 TEXT NOT NULL,
  task_id TEXT NOT NULL UNIQUE REFERENCES task(id),
  kept_at TEXT,                            -- «Годится»; NULL — не отобран
  UNIQUE (batch_id, ord), UNIQUE (batch_id, seed)   -- И16
);

CREATE TRIGGER image_variant_inputs_are_frozen BEFORE UPDATE OF
  batch_id, ord, seed, inputs_json, inputs_sha256, task_id ON image_variant
BEGIN SELECT RAISE(ABORT, 'image variant inputs are immutable (И14)'); END;
```

Статус и результат варианта **не хранятся дважды**: статус — `task.status`, картинка —
`task.result_asset_id` → `asset` (`kind='image'`, `origin_kind='take_output'`, `origin_task_id`, как кадр
Krea в плане S2–S3 R-S2-7). Ресурс неизменяем (И7), поэтому сцена или кастинг, получившие `asset_id`,
держат ровно те байты, что владелец отобрал.

Канонический JSON входов варианта (ключи отсортированы, `ensure_ascii=False`; `inputs_sha256` — хеш
строки). Это ровно то, что подставляется в граф, плюс версия шаблона:

```json
{"executor":"comfy","template":{"id":"qwen-image-t2i","sha256":"…"},"profile":"fast",
 "prompt":"<prompt_en дословно>","negative":"<текст карточки>",
 "lora":{"name":"Qwen-Image-2512-Lightning-4steps-V1.0-bf16.safetensors","strength":1.0},
 "width":1344,"height":768,"steps":4,"cfg":1.0,"seed":1847263}
```

`prompt` — `prompt_en` дословно (русский текст во входы не входит: в модель он не уходит). `negative`
— текст карточки у моделей с `uses_negative` (Qwen), иначе `null`; `cfg`, `steps` по умолчанию и `lora`
— из профиля карточки (`lora` у Krea 2 и Z-Image — `null`; сила в примере — заглушка, значение берётся
из карточки). Профиль входит во входы, поэтому повтор по сиду воспроизводит и Lightning.
Версия движка (`engine_version`) во входы не входит, а пишется в `task.engine_version` перед отправкой
(план S2–S3 R-S3-3): известна только к отправке.

Каталог файлов: `<outdir>/studio/projects/<pid>/images/<task_id>/f_00001_.png`.

### 19.8. «Сценарист картинки» (`studio/director/image_prompt.py`)

Через `provider.chat` (`:937`) со строгой схемой `STUDIO_IMAGE_PROMPT_SCHEMA`, системный промпт
`studio/director/prompts/image_prompt.md` (версия — в `prompt_llm_json`).
Язык (решение владельца §17.1 п.11 в): **владелец читает и правит русский, в модель уходит английский
перевод от «Сценариста»**, он виден и правится. Две схемы, один модуль:
- `mode:"idea"` — вход: идея, выбранная модель и её `text_render` из карточки, текущее соотношение
  сторон. Выход LLM: `prompt_ru` (развёрнутое описание кадра по-русски: объект, действие, окружение,
  свет, камера/объектив, фактура — словами устройства и сюжетной съёмки, а не «плёнка/зерно» — память
  «словарь реализма H3»), `prompt_en` (перевод того же текста, не пересказ), `inscriptions[{text, lang}]`
  (надписи дословно, на языке идеи), `suggested_aspect`.
- `mode:"translate"` — вход: `prompt_ru` и прежний `prompt_en` (чтобы перевод менял только изменённые
  места, а не переписывал всё); выход: `prompt_en`, `inscriptions`.
- **Код, а не LLM**: проверяет, что каждая надпись стоит в обоих текстах дословно в кавычках и **не
  переведена** (кириллическая надпись остаётся кириллицей в `prompt_en`, иначе дописывает
  `with the text "<надпись>"`); соотношение сторон не применяет; находки LI1/LI3/LI8 считает линтер.
- Перевод, пришедший к уже изменённому `prompt_ru` (номер `prompt_ru_version` разошёлся), не пишется —
  409, мастер перезапрашивает; так английский всегда соответствует русскому, который владелец видит.
- CAILA недоступна → 502 `llm_unavailable` (как O25); путь от LLM не зависит: английский промпт
  пишется руками в поле «В модель уйдёт» (O29, `prompt_en_state='owner'`).

### 19.9. Исполнение

- Вид задачи — существующий `image` (план S2–S3 задача 8): `ImageKind.spec` берёт значения из
  `payload.values` по `card.inputs` шаблона (а не фиксированным списком), `dest_dir` —
  `projects/<pid>/images/<task_id>/`; проверка результата та же: один PNG ровно запрошенного размера,
  иначе `failed` (`VerifyError`); `estimate_sample` пишется по `(executor, template, machine, w, h, 0, steps)`.
- Адаптер не меняется, кроме `probe`: `missing` (§8.1) и запись инвентаря моделей в
  `SETTING comfy.inventory` при каждом успешном `probe` — источник `installed` в O32 и LI7.
- Порядок: `priority=10` у картинок (§8.4); внутри партии — по `ord`, варианты партии идут подряд;
  партии разных моделей — по времени постановки (воркер не переставляет чужие партии ради экономии
  смены, чтобы порядок на экране совпадал с порядком нажатий).
- **Вытеснение.** На карте 64,9 ГБ Qwen (≈49 ГБ) и H3 (≈52,6 ГБ) вместе не держатся; ComfyUI сам выгружает
  одну, загружая другую (§8.2). Поэтому цена смены считается по фактической последовательности задач,
  включая очередь рендера: партия Qwen, вставшая перед ждущим рендером, получает в плане две строки —
  «загрузка Qwen +19 с» («Полное» +26) и «возврат H3 для очереди рендера +38 с». Мастер показывает обе в
  кнопке («≈ 11 с + смены 57 с»), чтобы владелец видел, что картинка задержит ролик. Krea 2 и Z-Image
  тоже вытесняют H3 (пик H3 + Krea выше карты), их цена — та же формула со своим `switch_in_s`.
- `POST /free` между моделями не шлётся: в цепочке Qwen → Z → Krea → H3 → Qwen OOM не было, худший пик
  53,9 ГБ, `/free` время не меняет (IMG-22). Флаг карточки `free_before_switch` есть в договоре на
  будущие модели, у трёх нынешних — `false`.

### 19.11. Тесты и мутации S2b

На имитациях (`FakeComfyStudio` плана S2–S3 + шаблоны картинок): PNG имитации детерминирован по
`(template, prompt, seed, steps, cfg, width, height)` и несёт эти значения в метаданных, поэтому смена
любого входа меняет пиксели. Сравнение повтора — **по декодированным пикселям**, не по sha256 файла.
Контракт шаблона — граф литералами теста (узлы, связи `positive ← 4`, `latent ← 6`, `model ← 7 ← 1` у
Z-Image, сид, шаги, cfg, shift, размер, `filename_prefix`), а не сравнение с `build_payload` (урок
блокера ред. 3 плана S2–S3).

Мутации, которые тесты обязаны ловить (каждая показана красной в отчёте среза, с текстом ошибки):
1. повтор генерирует новый сид вместо сида варианта; 2. авто-сид не передаётся — в граф уходит сид
по умолчанию шаблона; 3. партия одной задачей с `batch_size=N`; 4. снять триггер И14; 5. поменять
местами `width`/`height` при подстановке; 6. инвертировать условие LI1 (кириллица у Krea даёт warning,
у Z-Image — нет); 7. LI2 пропускает сторону, равную `side_max + sides_multiple_of`, или не проверяет
`max_pixels`; 8. O30 не сверяет `draft_edit_version`; 9. O31 отбирает вариант с `failed`-задачей; 10.
O28 над видеопроектом проходит; 11. шаблон варианта берётся из текущего черновика, а не из плана;
12. в граф уходит `prompt_ru` вместо `prompt_en`; 13. правка `prompt_ru` не делает перевод `stale`
(LI8 молчит, план проходит со старым английским); 14. профиль Qwen не входит во входы — повтор
«Быстро» уходит без LoRA на 50 шагах.

Сквозной тест (`tests/test_studio_image_path.py`): O2 image → O28 (ScriptedLlm) → O29 → O10 → O30 →
воркер → O31 → O10 repeat → O30 → воркер → пиксели равны → O2 video → O7 одна сцена → O8 с `asset_id`
варианта → O3 видеопроекта показывает кадр; события по видам и порядку — точным списком.
